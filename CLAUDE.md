# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A WSO2 reference implementation of an Open Banking standard for non-regulated markets (blending UK, Australian, Berlin Group and US FDX ideas). It does not contain the Open Banking accelerator itself. It contains the **service extensions** the accelerator calls out to, a **demo bank backend**, the deployment **artifacts** (API specs, RAR schemas, config snippets) needed to wire WSO2 IS / APIM up to them, and an **automated setup** that does all of it.

Target products: WSO2 API Manager 4.7.0, WSO2 Identity Server 7.3.0, and the WSO2 Financial Services accelerators 4.0 (`wso2-fsam-accelerator-4.0.0` for APIM, `wso2-fsiam-accelerator-4.0.0` for IS).

## Docs and terminology

- `README.md`: what the repo is, the actors, the artifacts and code, and the client application settings.
- `TRYOUT.md`: the manual, step-by-step setup (14 steps) ending with calling the APIs in Postman.
- `setup/README.md`: the automated setup.

Use the repo's terms in all docs: **customer** (owns the accounts, approves consents), **client application** (the third-party app calling the APIs), **the client application's developer** (signs up in the Developer Portal and creates the app), **bank**, **bank admin** (approves requests in the APIM Admin Portal), **user token** (authorization code, tied to a consent) and **client token** (client credentials). Don't use "TPP". The README's Actors table lists the synonyms from other standards.

## Build

Maven multi-module project (Java 1.8, parent `org.wso2:wso2:5`). There are no unit tests.

```bash
mvn clean install                                  # build both WARs
mvn clean install -pl non-regulated-ob-service-extension   # build one module
```

The WSO2 parent POM runs **checkstyle and findbugs during the build**, so style violations fail it. Checkstyle skips `src/gen/java/`. Each module's findbugs filter is `src/main/resources/findbugs-include.xml`.

The WAR names use `#` so they map to context paths: `non#regulated#ob#service#extension.war` deploys at `/non/regulated/ob/service/extension` (in IS), and `non#regulated#ob#demo#backend.war` at `/non/regulated/ob/demo/backend` (in APIM). `WEB-INF/lib/*.jar` is left out of the WARs because the host WSO2 server supplies the libraries (CXF, Jackson, etc.).

## Architecture

### `non-regulated-ob-service-extension`

A JAX-RS (Apache CXF) webapp that implements the accelerator's service-extension contract. The accelerator POSTs to it at defined points in the consent lifecycle and gets back a decision or enriched data.

- `src/gen/java/.../api` and `.../model` hold stubs generated by OpenAPI Generator (`JavaJAXRSSpecServerCodegen`) from the accelerator's service-extension spec. There is one `*Api` class per extension point. Stubs that aren't implemented return `"magic!"`.
- An extension is "implemented" when **all three** of these are true:
  1. the generated `*Api` method has been hand-edited to delegate to a static method in `src/main/java/.../impl/*ApiImpl`;
  2. the `*Api` class is listed in `jaxrs.serviceClasses` in `src/main/webapp/WEB-INF/web.xml`;
  3. the matching extension is enabled on the accelerator side (`allowed_extensions` under `[financial_services.extensions.endpoint]` in IS's `deployment.toml`; the setup's `deploy` phase sets this).

  Right now only `PopulateConsentAuthorizeScreen`, `PersistAuthorizedConsent`, `ValidateConsentAccess`, `PreProcessConsentRevoke` and `MapAcceleratorErrorResponse` are wired. If you regenerate the stubs, the delegation edits are lost, so re-apply them.
- The `impl/*ApiImpl` classes are thin routers. They branch on the consent's RAR `type` (`account_information_v1.0` vs. the payment types, checked with `CommonUtil.isPaymentType`) and hand the request to a per-domain util: `AccountConsentValidatorUtil`, `PaymentConsentValidatorUtil`, `ConsentScreenUtil`, `ConsentPersistUtil`, `ConsentRevokeUtil` or `ErrorMappingUtil`. Responses are built with `SuccessResponseUtil`, `FailedResponseUtil` and `ErrorResponseUtil`.
- Consents are expressed as **Rich Authorization Requests** (`authorization_details`, RFC 9396), not as an OB-specific consent-initiation API. `CommonUtil.getAuthorizationDetails` pulls them out of the request parameters.
- Payment consents can't be revoked: `PreProcessConsentRevokeApiImpl` only accepts `account_information_v1.0`. `artifacts/apis/README.md` explains why.
- `configurations/ConfigurableProperties.java` holds the deployment knobs as constants: demo-backend URLs for sharable/payable accounts (APIM's plain HTTP port `9763`), payment limits, cut-off policy, consent validity, and optional validations. `HttpClientUtil` calls the backend URLs when it builds the consent screen and validates debtor accounts.

### `non-regulated-ob-demo-backend`

A mock bank core (CXF webapp) that knows nothing about consents. It has three servlets: `/services/bankaccounts/bankaccountservice/{sharable,payable}-accounts` (used by the extension), `/services/accounts/accountservice/...` and `/services/payments/paymentservice/{paymentType}[/{paymentId}]` (used by APIM's dynamic endpoint).

### `artifacts/`

- `apis/`: OpenAPI specs for the Account Information and Payment Initiation APIs, published in APIM, plus sample `authorization_details`. **Read `artifacts/apis/README.md` before changing API behaviour.** It explains per endpoint which token type applies (user vs. client, from the spec's `CustomerOAuth2Security` / `ClientOAuth2Security`), which policies run (MTLS, JWT claim based access on `aut`, consent enforcement → `ValidateConsentAccessApi`, and dynamic endpoint always last), and why payment consents have no DELETE and no funds-confirmation endpoint.
- `rar-schemas/`: JSON Schema (Draft 2020-12) for each RAR type, plus `scripts/register.sh` / `authorize-app.sh` (need `jq` and `curl`; `IS_HOST`, `IS_AUTH` and `APP_ID` env vars; `print` mode is a dry run). These register the types in WSO2 IS 7.3. See `artifacts/rar-schemas/scripts/README.md`. The scripts default to `https://localhost:9443` and `admin:admin`; with the accelerator, IS runs on `9446` with `is_admin@wso2.com:wso2123`. If you change a type's shape, keep the schema, `types.json`, the sample authorization details and the Java validators in sync.
- `devportal-km-configs/am-deployment-snippet.toml`: the client application fields for the APIM Developer Portal. Only the JWKS URI is visible; the rest are hidden FAPI 2.0 defaults (`private_key_jwt`, PS256, PAR, signed request objects, certificate-bound tokens, S256 PKCE). The README documents each one.
- `workflow-extensions/`: `workflow-extensions.xml` turns on approval for sign-ups, applications, subscriptions and key generation; `default-workflow-extensions.xml` is the original.
- `custom-synapse-error-formatter/`: a gateway sequence that formats errors as `{Code, Message, Errors}`.
- `postman-script/`: an end-to-end Postman collection covering all API success flows. It reads its settings from collection variables (`pm.collectionVariables`), not from an environment.

### `setup/` and the `ob-setup` skill

`setup/setup.sh <phase>...` (or `all`) automates `TRYOUT.md` end to end. The phases are `extract`, `update` (interactive: needs a WSO2 login, so the user runs it), `accelerators`, `certs`, `deploy`, `start`, `configure-apim`, `register-rar`, `onboard`, `postman`, and `stop`. `.claude/skills/ob-setup/` is the skill that collects the inputs and runs them; its `phases.md` and `troubleshooting.md` describe each phase.

- Settings come from `setup/setup.env` (copy of `setup.env.example`). Generated keys, IDs and the configured Postman collection go to `setup/.state/`. Both are git-ignored and hold secrets; never commit them.
- `lib/common.sh` loads the config and has the shared helpers. `lib/edit.py` makes idempotent, line-based edits to `configure.properties` and `deployment.toml`. `lib/jwk.py` builds the JWK/JWKS with openssl. `lib/wso2.py` makes the REST calls (APIM Admin/Publisher `v4`, Devportal `v3`, IS SCIM2 and application APIs) and uses only the Python standard library.
- Every phase must stay safe to re-run, and must work on macOS's bash 3.2 (`set -u` breaks on empty arrays).
- The `accelerators` phase runs the accelerator's `configure.sh`, which **drops and recreates** the databases named by `DB_PREFIX` and replaces `deployment.toml`, so `deploy` must run after it.
- The phases that call running servers (`configure-apim`, `onboard`) haven't been run end to end yet. `troubleshooting.md` lists what to check.

When you change how something is set up, change it in all three places: `TRYOUT.md`, the matching `setup/` phase, and the skill's `phases.md`.
